## M1 追加（ABI v2 能力五项：isolate / intercept / use / dispose / dispose_self）

宿主侧（crates/host/tests/abi_m1.rs，4 个）：
- abi_isolate_derives_a_realm_and_returns_a_usable_handle
    派生句柄可用且 bit63=1；隔离域内读根域服务必须 missing（realm 隔离的直接证据）。
- derived_handle_is_revoked_when_the_root_instance_unregisters
    根实例注销 ⇒ 排水 owner==root 的派生句柄；再解析是可读的「已失效」。
- derived_handle_does_not_receive_op_dispose
    排水 ≠ 通知：OP_DISPOSE 恰好一次、只发给实例句柄。
- a_derived_handle_never_resolves_as_an_instance
    位布局：bit63=1 的句柄对实例专属 op（provide/effect）必须真失败（服务不得借道落根域）。

宿主侧（crates/host/tests/abi_m1_use.rs，4 个）：
- abi_use_mounts_a_child_component_and_disposes_it_with_the_parent
    ctx_use + 假 PluginSource；子组件随父 fiber 卸载（effect 链）。
- abi_use_resolves_native_components_by_at_name
    `@native:<name>` 走 NativeRegistry；未注册的名字是可读错误（含名字）。
- abi_use_from_inside_a_callback_does_not_deadlock
    OP_CALLBACK 内部再进宿主（with_instance → mount）不得死锁（multi_thread + 10s 超时）。
- abi_dispose_self_marks_the_loader_row_disabled_and_persists
    自卸载：loader 行 disabled 且**落盘**；插件真的收到 OP_DISPOSE。

crates/abi（单元 1 个）：
- abi_isolate_degrades_on_a_truncated_host_api
    截断宿主（size 到 v1 边界）上五个新能力逐字段降级成「宿主不支持」可读错误。

## M2 追加（入站异步：dispatch_id / STATUS_PENDING / ctx_fulfill）

crates/host/tests/abi_m2.rs（9 个：7 红 + 2 守卫）：
- pending_inbound_continuation_is_settled_exactly_once
    一次挂起恰好结算一次；第二次 ctx_fulfill 是可读错误「不存在或已结算」。
- two_concurrent_dispatches_of_the_same_handler_settle_independently（G17）
    同一 handler 两条并发派发各自挂起、各拿自己的结算值（注册 id 当键会互相覆盖）。
- ids_do_not_collide_across_two_plugin_libraries
    跨库 dispatch_id 不碰撞（全局铸造）；跨实例结算被拒（表按实例隔离）。
- unregistering_an_instance_fails_its_pending_continuations
    注销排水：派发以「插件已卸载」结算、pending_len 归零（不挂死）。
- fulfill_on_a_stale_handle_is_rejected
    陈旧句柄 ⇒ 「已失效」。
- fulfill_goes_through_with_instance_and_respects_generation（守卫）
    旧代际「已失效」；新句柄进表后报「不存在或已结算」（代际校验真生效）。
- status_pending_is_not_confused_with_a_json_return_value
    挂起走状态码：`{"pending":true}` 作为合法返回值在**两个方向**都不会被误读。
- pending_is_observed_before_the_dispatch_returns
    确定性证明"先登记后调用"：回调内部看到恰好 1 条自己的挂起条目。
- sync_handler_path_is_unchanged（守卫）
    同步路径逐字不变：回调恰好一次、立即带回、无挂起残留。

crates/host/tests/abi_m2_timeout.rs（1 个，**独占进程**：看门狗是进程级设置）：
- dispatch_policy_timeout_settles_a_never_fulfilled_continuation_as_timeout

## M2b 追加（waterfall 跨 ABI：ctx_next + kind:"next"）

crates/host/tests/abi_m2b.rs（8 个：7 红 + 1 守卫）：

- chain_tail_runs_when_the_last_handler_delegates
    链尾（最后一个 handler 就 delegate）仍运行，且恰好一次；外层以 PENDING 返回。
- a_fully_synchronous_chain_still_requires_exactly_one_pending_round_trip
    全同步链也必须"返回 PENDING + fulfill"；`kind:next` 的**内联**投递由调用序钉死。
- unfinished_waterfall_frame_is_cleaned_on_unregister

## M3 追加（intercept 消费点：提供者读 `d(k) ⊕ ι(k)`，右偏）

crates/core/tests/intercept_meta.rs（6 个）：
- providers_see_the_merged_metadata_of_declaration_and_context
    提供者侧拿到的实参 = `merge(调用者的 inject 声明 d, context 携带的 ι)`：两路都必须到达。
- context_carried_metadata_overrides_the_component_declaration
    **右偏**：同键冲突时 context 的 `ι` 覆盖声明 `d`；声明里独有的键保留。
- nearest_intercept_layer_wins_over_an_ancestor
    链条优先级 = 最近 intercept 层 > 祖先 intercept 层 > 组件声明。
- changing_intercept_does_not_restart_the_fiber
    合并在**调用时**发生：调用点上再叠一层 ⇒ 提供者看到新元数据，而消费者与提供者
    fiber 的 uid、apply 次数都不变。
- service_config_reaches_the_plugin_through_resolved_config
    引擎便利通道 ②（**不是** Def 26 的 d(k)）：`ctx.resolved_config()` = 已解析的插件
    配置 + 每个**已声明**依赖在调用点上的合并结果（未声明的名字不出现）。
- intercept_metadata_survives_a_provider_replacement
    提供者换代（先卸后挂）后新提供者看到同一份元数据；消费者走了"依赖消失 ⇒ 卸载、
    回来 ⇒ 重装"一轮，恰好 apply 两次（元数据挂在调用点的链上，与提供者是谁无关）。

## M4 追加（scope / Filter：注册期 scope + 父键关系，**新原语**）

crates/core/tests/hook_scope.rs（6 个：5 红 + 1 守卫）：
- filtered_context_can_register_events_and_carries_the_fiber（G18）
    `filter` 派生的子 context **带调用者的 fiber**（`fiber()`/`fiber_opt()` 都看得见）
    ⇒ 在它上面注册事件是合法操作；三条作用域注册各自的 scope 都进 `hook_scopes` 诊断面；
    派发点没有 scope ⇒ 四条都跑（既有行为逐字不变）；派发点 = 自己的作用域 ⇒
    只跑"自己这一支 + 无 scope 的注册"。
- service_method_can_observe_the_callers_scope
    原生服务的方法用**调用者的 ctx** 做派发点 ⇒ 只有调用者那一支的拦截器参与
    （两个 agent 同名事件互不可见）——M11「每 agent 一个 scope」的机制。
- scope_parent_chain_is_queryable_and_rebindable
    父键关系可查询（`in_scope_of` 沿链）、**可重绑**（换父之后旧父不在链上）、
    反向不成立（父不继承子的可见性）。
- scope_parent_cycle_is_rejected
    成环/自绑被拒（可读错误含"环"），且拒绝时关系原封不动。
- realm_and_fiber_dispatch_filters_are_unaffected（守卫）
    既有两轴逐字不变：派发点没有 scope 时 scope 轴不参与，连"注册在带 scope 的
    ctx 上"的钩子也照旧由两轴裁决（Parallel 全跑、fiber 子树滤掉）。
- scope_survives_the_anchor_fiber_going_away
    作用域比 fiber 活得久：锚点只持 `Weak`（**派生不得增加 fiber 的强引用计数**，
    用 `Arc::strong_count` 钉死）；fiber 卸载后钩子摘除、装载表清空，而锚点身份
    与父键查询照旧。

## 缺陷 5 闭环：卸载"依赖装载器行服务的原生 fiber"之后插件对象被回收（4 条新测试）

`crates/host/tests/loader_release.rs`（新文件，4 条）：
- `unloading_a_row_after_its_calling_dependent_was_disposed_releases_the_plugin`（矩阵变体 (h)：依赖 + **调用** + 卸载）
- `unloading_a_row_after_an_intercept_derived_dependent_was_disposed_releases_the_plugin`（矩阵变体 (b)：依赖 + **派生 intercept ctx** + 卸载）
- `unloading_a_row_with_a_live_dependent_also_releases_the_plugin`（矩阵变体 (e)：依赖者**留在线上** ⇒ 退回 PENDING，插件对象照样回收）
- `the_probe_detects_a_deliberately_retained_plugin`（**反空转**：假源故意留一份 `Arc<dyn Plugin>` ⇒ 判据必须为假）

判据：**插件对象是否被 drop**（`SpyPlugin` 的 `Drop` 打标）——它就是二进制层"暂存副本能否删除"
的等价观测，且**不依赖动态库**；假源提供的服务值形态与 ABI 提供者同形
（`Dyn::new(...).with_adapter(adapter)`，adapter **握着提供者的 ctx**，与 `PluginIface` 同构），
所以它真的覆盖"被留下的 ctx 吊住提供者 fiber"那条入口。
夹具纪律：装载器**挂成一个插件 fiber**（行 fiber 是它的孩子）——否则量到的是缺陷 6
（"行 fiber 是 root fiber 的 effect ⇒ 永不回收"），不是缺陷 5。

### 结论与机制
`Arc<dyn Plugin>` 的长期持有面只有 `Store.runtimes[..].plugin` 与 `Fiber.runtime → Runtime.plugin`
两条，**两条都以"fiber 活着"为前提** ⇒ 缺陷 5 等价于"插件卸载后谁还握着那条 fiber"。
答案是 **`ctx → fiber` 曾经是强引用**：依赖者被卸载后，只要还有人留着它的 ctx
（依赖者提交视图里的 `Impl`、宿主的 `Instance.ctx`、派生的 intercept ctx），提供者的 fiber
就被一起吊住。**M4 的 G18 已把它改成 `Weak<Fiber>`**（根 fiber 由 `Store.root_fiber` 强持）
⇒ 链断；原记录里"最可能是 `Mounted.plugin` / watcher 没放手"的猜测**不成立**。

## M8-后续②：流式 op（ADR 0001 §5 的落地，`call_iface_stream`）

**新增 14 条测试**（210 → 224）：core 9（`crates/core/tests/stream.rs`）+
host 5（`crates/host/tests/abi_stream.rs`）。

### 契约（本里程碑定稿）
- 调用方：`Context::call_iface_stream(service, version, method, args) -> Result<AsyncStream>`；
- 提供者（跨 ABI）：`ctx_stream_push(dispatch_id, chunk, on_credit)`（#20）、
  `ctx_stream_close(dispatch_id)`（#21）、`ctx_stream_fail(dispatch_id, reason)`（#22）；
- 窗口 `STREAM_WINDOW = 4`；满窗口的推送返回 `STATUS_PENDING` 且**块没被接受**；
  消费者每取走一块 ⇒ 宿主以 `kind:"stream-credit"` 回调**那条续延 id**
  （载荷 `{"result":{"window":n,…}}`；`{"error":…}` = 流没了，停手）；
- **插件的返回值 = 长度 1 的流**（不写流式代码的提供者也能按流调用；`ExternService::call_stream`
  的默认实现就是它）；
- 收尾恰好一次（close / fail / 消费者丢弃）：close **不丢缓冲**、fail **立刻给 Err**
  （缓冲丢弃——与真实 LLM 流的处置一致）；
- 卸载 / 取消 / 超时 / 消费者离场 ⇒ **先排水**：等待中的 credit 被驳回、流以**错误**结束、
  记录连同帧一起摘掉（`pending_len` / `waterfall_len` / `streams_len` 全归零）。

**与 ADR §5 的三处偏离（有意，ADR 里已注记）**：① 不设 `open-stream`——"流"就是那次派发本身
（复用 `dispatch_id`），少一个 id 空间与一次往返；② ADR 的 "abort" 定名 `stream_fail`
（与宿主→插件的 `ctx_abort` 区分开）；③ 额度由 `next()` 隐式归还（一名额一次回调），不引入
额外 API（ADR 里的 `credit()` 因此不需要）。

### 红档（先红后绿）
- 首跑即**编译红**：core `E0432`（`StreamSink`/`AsyncStream`/`PushOutcome`/`StreamObserver`/
  `StreamOutcome`/`STREAM_WINDOW` 未导出）+ `E0407`（`call_stream` 不是 trait 成员）；
  host `E0432`（`KIND_STREAM_CREDIT`/`STATUS_STREAM_GONE`/`streams_len`）+ `E0609`（三个
  `ctx_stream_*` 字段不存在）+ `E0599`（`call_iface_stream` 不存在）。
- 实现中间态红：`Dyn::adapter` 返回 `Arc<dyn ExternService>`（不是 `IfaceRef`）⇒ `iface_target`
  的返回类型与 `version`/`methods` 调用点都得跟着改；`match` 两臂类型不一致（E0308）；
  `DispatchRecord` 缺 `stream` 字段（E0063）；sdk.rs 少导入 `STATUS_STREAM_GONE`
  ⇒ 模式匹配把它当**变量**（E0408）；夹具 `MutexGuard` 未 `mut`（E0596）。
- 夹具纠错 1 处：`loaded_instances()` 是**进程级**计数，并行跑的其他测试也在挂插件 ⇒
  卸载用例不能断言它为 0（改成 `streams_len(handle) == 0` + `pending_len(handle) == 0`）。

### 非空验证（mutation，三条，全部变红）

### 验收（ADR §5 的口径）

### 缺陷 7：装载器收尾期"晚到的一轮对账"往已拆掉的 `loader.report` 写值

- **现象**：demo 快照约 **1/20** 的概率多 107 字节 ——
  `length mismatch: expected 5079 bytes, actual 5186 bytes`，多出来的正是
  `[WARN ] cordis:include: 刷新 loader.report 失败: cannot set property "loader.report" without provide`。
- **判定**：不是异常，是**正常时序**。`loader.report` 的提供者**就是装载器自己**
  （`load_with_source` 在 `provide` 之后才 `mark_report_published`），装载器拆到一半
  （`Unloading`/`Disposed`）或依赖没齐（`Pending`）时这一写必然失败。
- **修复**：`crates/host/src/loader.rs::publish_report` 在**装载器自己不在
  `FiberState::Active`** 时直接返回（与 `attach_self_dispose_observer` 的第 2 条判定同源）；
  只有"还 ACTIVE 却写不进自己的报告"才继续报警。
- **回归（新 1 条）**：`crates/host/tests/loader_reconcile.rs::
  a_reconcile_after_the_loader_fiber_is_disposed_does_not_publish`
  —— 装载器挂在一个**自己的**插件 fiber 下 ⇒ 拆掉 ⇒ 再来一轮 `sync()` ⇒
  断言日志里没有那句话、且 `loader.report` 已随提供者消失。
  具名修改：`loader_reconcile.rs` 的 import 行加 `FiberState`。
- **非空验证（mutation）**：去掉守卫 ⇒ 该条红（`收尾期不许再发布报告`）。
