rust-cordis → Harness RSI 自演进 SDK 底座
改造方案 v2 · 2026-11-18 · 已经三轮评审并修订

一句话：rust-cordis 不进演化循环，它是演化循环下面那块地板——已选中变体的部署宿主（装/换/回滚）、 调用级归因数据源（谁调了谁、花了多久、成没成）、契约冻结门禁（只许改实现，不许改服务方法名集合）。 三件事都是在现有能力上补出口：不动 ABI、不加 CLI 面、不引入 Wasm。阶段 1 约 14 人日。
2026-11-18 决策已定：D1 修 ADR 0005，允许"受审流水线签发"的演化产物进入运行时（WP0 第 4 项）；D2 同意两个月接入门，无 Rust 消费者则阶段 2 只做子进程载体。方案不再有待决项。
WP0 验收后的修正（三轮独立评审两轮，见 docs/review-r1/r2/r3.md）： ① 签发只是准入口径，不是 loader 能力 —— attestation 由准入步骤核对，且必须绑定 artifact SHA256 与 variant revision，否则可重放； ② 契约锁只能锁方法名集合（ExternService::methods() 无参数形状），IO schema 级锁列为范围外； ③ 归因埋点必须用共享 outcome cell + Drop guard：超时/取消/panic 三条丢弃路径不能都记成 timeout； ④ 新增"callee panic 仍产出 Err 记录"断言（宿主写记录 vs 插件自报的硬证据）； ⑤ callee_uid 在发起时快照（卸载后是 u64::MAX），并加稳定的 callee_plugin；不引入 mount_gen，在飞热换不承诺归到正确那一代； ⑥ 导出面目前不存在：WP2b 需新增 Store::services_of(&Arc<Fiber>)（薄封装 impls_owned_by）与 StatusReport.capabilities（typed row），方法名在 shutdown 前抓取； ⑦ attestation 摘要不写进 policy JSON（未知字段会被静默丢弃），放准入台账；准入合并须与签发流水线职责分离； ⑧ "变体不得用 dev_unverified"只是部署纪律，loader 不区分变体，无法强制——已在 ADR 里如实说明； ⑨ trace sink 的安装入口挂 App，不挂公开可达的 Context::store，否则同进程插件可以替换或摘除记录。
v1 → v2 的三处结构性修正（来自评审，详见 §8）： ① 评估期不在本宿主热换变体（每变体一进程是外部循环的事，dylib static 会跨变体泄漏）；宿主的热换/回滚只用于部署已选中变体 + 金丝雀回滚。 ② 阶段 1 只追踪服务接口调用（call_iface），不追踪事件派发——事件路径产不出失败结果，且验收场景无消费者。 ③ cordis status --json 是"新起 App 挂一下再关"，不能观测运行中宿主；示例改为自定义 Rust 宿主 + 进程内 e2e，不写 Python 驱动脚本。

0. 前提假设与解释空间

#假设若不成立的后果
A1演化循环在外部（Python/TS + 容器 + git）：生成变体、评估、选父代、归档都不由 rust-cordis 做。若要求 Rust 内做 LLM 调用/选择策略，是另一个项目，本方案作废。
A2"SDK 底座"= 四样东西：插件契约（接口与实现分离）、部署宿主（装/换/回滚）、观测（调用级归因）、治理约束（评估器不在演化写入面上）。若指给 LLM 写插件的 DSL/生成器，该做在 TS 侧。
A3不升 ABI major：改动全部是 T1/宿主内部，或 ADR 0004 允许的尾追加。阶段 1 实际不碰 ABI。接受升 major 则 T2 异步化可提前。
A4消费者接受文件驱动（替换 cdylib + sidecar manifest + 改 YAML），宿主通过 HMR 轮询拾取；观测通过宿主自己落盘的 JSONL/JSON 文件。不提供 RPC。需要 RPC 则阶段 2 的 loader.control 提前。
A5′进本宿主的只有已选中变体，带受审演化流水线签发的 sidecar manifest（sha256 + source_revision + 流水线 revision + 评估记录摘要）。宿主不运行未经评估的 LLM 产物。签发权已由 D1 决定：修 ADR 0005 承认"受审流水线"为签发方。若要在宿主里直接跑未评估产物，必须先有子进程/Wasm 载体（阶段 2）。
A6评估 episode 在宿主内串行执行；trace 用墙钟时间戳与 episode 时间窗对齐。并行 episode 需要 correlation 透传（阶段 2 S2-2）。

两种理解，本方案选第一种

  • 理解甲（选）：RSI 底座 = 演化产物的部署与观测地板。复用 loader/volatile/回滚/inject 声明，补出口。
  • 理解乙（不选）：RSI 底座 = 演化循环本身的运行时。Hyperagents/PluginRSI 已用 Docker+git+Python 解决，Rust 内核无差异化。

WP1 · 服务调用归因（trace sink，iface-only） 4.5 人日 核心

目标每次经 call_iface 的跨 fiber 服务调用产出一条记录，足以回答"调用链 A→B→C 里哪一跳失败/变慢"。
设计 
// crates/core/src/trace.rs（新文件，约 60 行）
pub struct TraceRecord {
    pub ts_ms: u64,          // 完成时刻，供与 episode 时间窗对齐（A6）
    pub name: Box<str>,      // "service.method"
    pub caller_uid: u64,     // root ctx 的 fiber_opt() 返回 UID_ROOT，不需要 Option
    pub callee_uid: u64,     // 发起时快照（drop 时读会得到 u64::MAX）
    pub callee_plugin: Box<str>, // 运行时名，跨热换稳定
    pub elapsed: Duration,   // 含 PENDING 等待期（PluginIface::call 内部已 await settle）
    pub outcome: Outcome,    // Ok | Err(code)：host_timeout / host_cancel / host_panic / host_drop
}
pub trait TraceSink: Send + Sync { fn record(&self, r: TraceRecord); }
impl App { pub fn set_trace_sink(&self, sink: Arc<dyn TraceSink>); }  // 挂 App，不挂公开的 Store
  • 两个记录点，按"谁先知道结果"分工：正常完成在 Context::call_iface（context.rs:468-486，T1→T2 与 T2→T2 的汇合点，host 的 ctx_call_iface 也调它）；异常终止在宿主调用包装层——超时（with_iface_timeout，lib.rs:1936）、取消（complete_or_defer 的 None 分支）、panic 都只有那一层知道。两处互斥，各发一条。
  • 不要把三条异常路径塞进 core 的 Drop guard：future 被超时丢弃时 core 的收尾不执行，且 guard 判不出原因（panic 已被 catch_unwind 截断，future 是正常析构的）。异常码用宿主已有的 host_timeout/host_cancel/host_panic；只有宿主未分类的丢弃才记 host_drop。
  • 安装入口挂 App，不挂 Store：Context.store 是公开字段，插件能触达；挂 Store 上等于让插件可以替换/摘除记录。
  • callee 身份：补 Store::resolve_impl 返回 Arc<Impl>（现 resolve 丢掉 Impl.fiber），在发起时取 provider_uid()（store.rs:86）与运行时名。约 20 行。
  • 零开销：sink 槽用 OnceLock<Arc<dyn TraceSink>>，未安装时一次原子读早返回，不取 Mutex。
  • call_iface_stream（context.rs:495）阶段 1 明确排除，写入 ADR。
  • sink 实现放示例宿主（WP4），写 JSONL；不加 cordis run --trace-out，不在 host crate 放 JsonlSink。
不做事件派发追踪（事件 Ret = Option<Dyn> 不可失败，event.rs:12；阶段 1 无消费者。若将来要做，单点在 Store::handlers() store.rs:1218-1248 包每个 hook）；采样/聚合/OTel；correlation 透传。
验证
  1. cargo test -p rust-cordis-core trace_iface_chain：A 经 call_iface 调 B，B 调 C，C 返回 Err → 2 条记录：(A→B, Err)、(B→C, Err)，uid 与 name 正确。
  2. cargo test -p rust-cordis-host trace_iface_pending：T2 插件返回 PENDING，50ms 后 fulfill → 1 条记录 outcome=Ok、elapsed ≥ 50ms。
  3. cargo test -p rust-cordis-host trace_iface_abort_paths：超时 → 恰好 1 条 host_timeout；取消 → 1 条 host_cancel；panic → 1 条 host_panic；三者写成同一个码时前两条红。
  4. cargo test -p rust-cordis-host trace_iface_inflight_swap：PENDING 期间热换，记录带发起时 uid 且 callee_uid != u64::MAX。
  5. cargo test -p rust-cordis-host trace_iface_panic：callee apply/回调 panic → 仍产出 1 条 Err（"宿主写记录"的硬证据）。
  6. 未装 sink：代码评审确认 call_iface 路径只多一次 OnceLock::get；不写性能测试。
  7. 回归：cargo test --workspace --all-targets --locked 全绿；cargo test -p cordis-abi 与 baseline.txt 不变。

validate --interface-lock —— 不加 CLI flag，10 行 diff 即可。注意 inject.required 混合了 YAML 行级声明（lib.rs:196），锁比对用插件声明口径或接受"行+插件"口径，ADR 写明。

范围限定：ExternService::methods() 返回 Vec<String>，只有方法名；参数/返回值在 ABI 上是 Config，宿主看不到形状。所以契约锁只能发现增删改名，发现不了参数类型变化。IO schema 级锁需要给 PluginDesc 按方法加 args/ret schema，属独立设计决策，不在阶段 1。

验证cargo test -p cordis-cli status_services_methods：fixture 插件 provide_iface 两个方法 → services[0].methods.len()==2；WP4 e2e 验收 3 覆盖"删除/改名方法被拒"。

WP4 · 端到端示例：examples/rsi-substrate 5 人日 验收载体

场景 部署金丝雀（不是评估期）：已选中变体 solver-v2 带 manifest 投放到运行中宿主；canary evaluator 跑 5 个固定用例；trace 把回归归到调用链中 solver 而非 pipeline；驱动方据此改回 YAML → 回滚。

验证（e2e 断言）
  1. v1：score 5/5；trace 中 evaluator→pipeline 5 条 Ok、pipeline→solver 5 条 Ok。
  2. 投 v2：热换成功、solver uid 变、sha256 变；trace 中 pipeline→solver 2 条 Err 且 evaluator→pipeline 对应 2 条 Err —— 按 callee_plugin/callee_uid 聚合，solver 行 40%、pipeline 行 0%（自身无失败，仅透传）；改回 YAML → uid 再变，同一用例回到 Ok。金丝雀的硬判据是"同一用例 Ok→Err"或"出现 callee_plugin=solver 的新 Err"，不是分数（同进程 static 污染使跨代分数不可比，ADR 0009 §3）。这一步证明归因可定位到链中一跳。
  3. 投 v3 前做契约 diff：services[solver].methods 少了/改名了，或 iface_spec_sha256 与 manifest 不符 → 拒绝投放；宿主无感知。
  4. 投 solver-panic：SwapOutcome::RolledBack；report.failed 含 solver；uid 变为新值（回滚会重建 fiber），sha256 回到 v1 的值，evaluator 仍 5/5。用例本身必须幂等：apply 失败回滚复用同一模块（static 保留），改 YAML 重投是新模块（static 全新）。
  5. 投 solver-crash：solve 回调 panic → 恰好一条 Err 记录且 callee_plugin = solver；宿主不退出。这是"记录由宿主写、插件无法自报"的硬证据。
  6. 在飞热换：让 pipeline 的调用在 PENDING 期间触发 solver 热换 → 该记录仍带发起时 uid（!= u64::MAX）与 callee_plugin=solver，不因 drop 读已释放实例而丢归属。
  7. 全程同一 App 实例（不重启）；Windows + Linux 均通过（CI --workspace 自动覆盖）。
风险示例 manifest 必须含 attestation 三项 + iface_spec_sha256（D1 后 sidecar 是示例要证明的东西，不再保留 set_allow_unverified(true) 退路）。PluginSourcePolicy::verify 不校验 attestation：示例宿主的准入函数自己做交叉核对（eval-record 的 artifact SHA256/variant revision ↔ manifest），并遵守职责分离（合并准入者 ≠ 签发流水线）。
