rust-cordis → Harness RSI 自演进 SDK 底座
改造方案 v2 · 2026-11-18 · 已经三轮评审并修订

一句话：rust-cordis 不进演化循环，它是演化循环下面那块地板——已选中变体的部署宿主（装/换/回滚）、 调用级归因数据源（谁调了谁、花了多久、成没成）、契约冻结门禁（只许改实现，不许改服务方法名集合）。 三件事都是在现有能力上补出口：不动 ABI、不加 CLI 面、不引入 Wasm。阶段 1 约 14 人日。
2026-11-18 决策已定：D1 修 ADR 0005，允许"受审流水线签发"的演化产物进入运行时（WP0 第 4 项）；D2 同意两个月接入门，无 Rust 消费者则阶段 2 只做子进程载体。方案不再有待决项。
WP0 验收后的修正（三轮独立评审 + 多轮 A1/A2/A3 角度验收，见 docs/review-r1/r2/r3.md）： ① 签发只是准入口径，不是 loader 能力 —— attestation 由部署准入台账核对，且必须绑定 artifact SHA256 与 variant revision，否则可重放； ② 契约锁只能锁方法名集合（ExternService::methods() 无参数形状），IO schema 级锁列为范围外； ③ 归因写入点：core 在入站派发记录之前（解析/版本/方法检查失败）；host 在同步出口或 PENDING 结算（共用 dispatch_id、互斥）；host 在“入站从未结算”时有三种补写：仅出站看门狗超时（call_id=0、HOST_TIMEOUT）、poll 边界 panic（call_id=0、host_panic）、NoRuntime（call_id=0、host_call）； ④ panic 分两种断言：宿主 poll 边界 unwind → call_id=0、host_panic；T2 插件经 ABI 收敛的 STATUS_ERR 走入站结算（真实 call_id）； ⑤ callee_uid 在发起时快照（结算时是 u64::MAX），并带稳定的 callee_plugin；不引入 mount_gen； ⑥ 导出面已落地（WP2b）：Store::services_of(&Arc<Fiber>)（复用 impls_owned_by 的 fiber 身份判据）与 StatusReport.capabilities（typed row，含 services），方法名在 shutdown 前抓取； ⑦ attestation 摘要不写进 policy JSON（未知字段会被静默丢弃），放准入台账；准入合并须与签发流水线职责分离； ⑧ "变体不得用 dev_unverified"只是部署纪律，loader 不区分变体，无法强制——已在 ADR 里如实说明； ⑨ trace sink 的安装入口挂 App，不挂公开可达的 Context::store，否则同进程插件可以替换或摘除记录； ⑩ 父链设计见 ADR 0010：`call_id` 复用入站 `dispatch_id`，host 新增私有 CALL_SCOPE，只在 call_inbound 执行窗口与 deliver_outbound 交付窗口压栈；不改 ABI、不加 HostApi 字段； ⑪ 父链的边界已披露：T1 异步起点、事件/waterfall 起点、typed 直调与流式接口无父；T2→T1→T2 跳过 T1。事件不压 CALL_SCOPE，避免父指向无记录的幽灵 id。
v1 → v2 的三处结构性修正（来自评审，详见 §8）： ① 评估期不在本宿主热换变体（每变体一进程是外部循环的事，dylib static 会跨变体泄漏）；宿主的热换/回滚只用于部署已选中变体 + 金丝雀回滚。 ② 阶段 1 只追踪服务接口调用（call_iface），不追踪事件派发——事件路径产不出失败结果，且验收场景无消费者。 ③ cordis status --json 是"新起 App 挂一下再关"，不能观测运行中宿主；示例改为自定义 Rust 宿主 + 进程内 e2e，不写 Python 驱动脚本。

0. 前提假设与解释空间

#假设若不成立的后果
A1演化循环在外部（Python/TS + 容器 + git）：生成变体、评估、选父代、归档都不由 rust-cordis 做。若要求 Rust 内做 LLM 调用/选择策略，是另一个项目，本方案作废。
A2"SDK 底座"= 四样东西：插件契约（接口与实现分离）、部署宿主（装/换/回滚）、观测（调用级归因）、治理约束（评估器不在演化写入面上）。若指给 LLM 写插件的 DSL/生成器，该做在 TS 侧。
A3不升 ABI major：改动全部是 T1/宿主内部，或 ADR 0004 允许的尾追加。阶段 1 实际不碰 ABI。接受升 major 则 T2 异步化可提前。
A4消费者接受文件驱动（替换 cdylib + sidecar manifest + 改 YAML），宿主通过 HMR 轮询拾取；观测通过宿主自己落盘的 JSONL/JSON 文件。不提供 RPC。需要 RPC 则阶段 2 的 loader.control 提前。
A5′进本宿主的只有已选中变体，带受审演化流水线签发的 sidecar manifest（sha256 + source_revision + 流水线 revision + 评估记录摘要）。宿主不运行未经评估的 LLM 产物。签发权已由 D1 决定：修 ADR 0005 承认"受审流水线"为签发方。若要在宿主里直接跑未评估产物，必须先有子进程/Wasm 载体（阶段 2）。
A6评估 episode 在宿主内串行执行；trace 用墙钟时间戳与 episode 时间窗对齐。并行 episode 需要 correlation 透传（与调用链无关，另立设计）。

两种理解，本方案选第一种

  • 理解甲（选）：RSI 底座 = 演化产物的部署与观测地板。复用 loader/volatile/回滚/inject 声明，补出口。
  • 理解乙（不选）：RSI 底座 = 演化循环本身的运行时。Hyperagents/PluginRSI 已用 Docker+git+Python 解决，Rust 内核无差异化。

S2-2 · 调用链关联设计（前置，已完成）0 人日 ADR 0010

父链语义与压栈点见 docs/adr/0010-call-graph-correlation.md：host 私有 CALL_SCOPE（thread-local + RAII），只在 iface 入站窗口与续延交付窗口压栈；Outbound 拆出 trace_parent，取消树的 DispatchRecord.parent 保持不变；PendingContinuation 携带 trace 父、traced、callee/发起方快照（不再重复存 call_id）。不改 ABI、不加 HostApi 字段。WP1 的实现包含它。

WP1 · 服务调用归因（trace sink，iface-only） 4.5 人日 核心

目标每次经 call_iface 的服务调用产出一条记录，足以按父链把失败定位到链中一跳（父子语义与压栈见 ADR 0010）。
设计 
// crates/core/src/trace.rs（新文件，约 50 行）
pub struct TraceRecord {
    pub ts_ms: u64,          // 完成时刻，供与 episode 时间窗对齐（A6）
    pub name: Box<str>,      // "service.method"
    pub call_id: u64,        // 入站 dispatch_id；解析失败/仅出站超时/poll panic/NoRuntime 为 0
    pub parent_call_id: u64, // 发起时的 CALL_SCOPE 栈顶；0=根/未归因
    pub caller_uid: u64,     // root ctx 的 fiber_opt() 返回 UID_ROOT，不需要 Option
    pub callee_uid: u64,     // 发起时快照（结算时读会得到 u64::MAX）；0=根或未记到
    pub callee_plugin: Box<str>, // 运行时名；callee_uid=0 时填请求名（根为 "root"）
    pub elapsed: Duration,   // 含 PENDING 等待期（入站 settle 覆盖）
    pub outcome: Outcome,    // Ok | Err(code)：HOST_TIMEOUT / host_cancel / host_panic / host_lifecycle / host_call / 业务码
}
pub trait TraceSink: Send + Sync { fn record(&self, r: TraceRecord); }
impl App { pub fn set_trace_sink(&self, sink: Arc<dyn TraceSink>) -> bool; }  // 挂 App，不挂公开的 Store
  • 写入点 = 调用产生最终结果的地方，一次调用只写一条：① core——iface_target 解析失败与随后的版本/方法检查失败（call_id=0）；② host——同步返回（STATUS_OK/STATUS_ERR/ABI 边界 panic）在 call_inbound 出口，STATUS_PENDING 在 settle 落定，两处共用同一 dispatch_id 且互斥；③ host——仅出站看门狗单独超时补写一条 call_id=0 的 HOST_TIMEOUT；④ host——出站 future 的 poll 边界 panic（首 poll / 后台）补写一条 call_id=0 的 host_panic；⑤ host——NoRuntime 补一条 call_id=0 的 host_call；③④⑤ 都与 ② 互斥。结果码：三类异常 HOST_TIMEOUT/host_cancel/host_panic；结算通道关闭 host_lifecycle，无法驱动 host_call；插件业务码原样透传；trace-only 内部码是 resolve_failed/iface_check_failed/status_<n>；plugin_unsupported/plugin_protocol 是既有协议码，trace 复用同名码。
  • 父链：新增私有 CALL_SCOPE（thread-local + RAII），只在两个窗口压栈——call_inbound 执行提供者代码的窗口、deliver_outbound 交付 OP_CALLBACK 的窗口；PluginIface::call 的 trace 父取 call_scope_top()，取消父仍取 scope_top()（Outbound 拆出 trace_parent）。事件/waterfall/流压的是 DISPATCH_SCOPE，不压 CALL_SCOPE。
  • 出站 iface_id 不进父链：它只做取消/结算记账；父链只用入站 dispatch_id，否则父会指向不存在的记录。
  • PENDING 要带父与快照：PendingContinuation 增 trace_parent、traced、callee 快照、caller_uid、name、started（不跨 FFI）；settle 只在 traced 为真时写记录；trace_parent 与取消树的 parent 是两个字段。
  • 取消只写一次：取消交付与超时/panic 同在入站结算路径；revoke_dispatch 等早退不写。
  • 结果分类靠错误码：HOST_TIMEOUT/host_cancel/host_panic。
  • 解析不到实现时也要记：callee_uid=0 表示“没有记到实现方”（解析失败/仅出站超时/poll 边界 panic/NoRuntime）。根提供者的 uid 也是 UID_ROOT=0，所以不能只看 uid 区分“根/未知”；未记到实现方时 callee_plugin 是请求的服务名，根实现时是 "root"，没有路径会产出空串。
  • 外部丢弃调用 future 时没有记录：调用方任务被整体取消、或自己 select! 掉 future，只剩宿主侧可观测的取消结果。
  • 安装入口挂 App，不挂 Store：Context.store 是公开字段，插件能触达；挂 Store 上等于让插件可以替换/摘除记录。
  • 零开销：sink 槽用 OnceLock<Arc<dyn TraceSink>>；未安装时每个入口一次原子读 + 一次时钟读，不取锁、不构造身份快照。
  • call_iface_stream（Context::call_iface_stream）阶段 1 明确排除，写入 ADR。
  • sink 实现放示例宿主（WP4），写 JSONL；不加 cordis run --trace-out，不在 host crate 放 JsonlSink。
不做事件派发追踪（事件 Ret = Option<Dyn> 不可失败，event.rs:12）；采样/聚合/OTel；跨进程链路拼接。

WP2b · 契约锁：含服务方法名 1.5 人日 已实现

改动
  1. status --json（挂载后导出，crates/cli/src/lib.rs:899-934）每行追加 services: [{name, version, methods: [..]}]，数据来自该 fiber 经 provide_iface 注册的 ExternService（dyn_value.rs:143）。约 40 行。
  2. 两个导出面已落地（WP2b）：Store::services_of(&Arc<Fiber>)（接收 fiber 而非裸 uid；UID_DISPOSED 返回空）按 Dyn::adapter 枚举可调用面，方法名排序去重；StatusReport.capabilities 是 typed row（仿 RowProvenance，StatusReport 仍可派生 Eq），每行带 services: [{name, version, methods}]。方法名在 status_with_source shutdown 之前抓取。`loader.report().capabilities[]` 同时补了插件自述的配置 schema，status --json 的契约子集可一次导出。
  3. 契约 = {inject, provision, schema, services, iface_spec_sha256}（inject 用插件声明口径，行级声明混入时须固定口径）。锁文件 = cordis status --json 的这一子集 + manifest 的 iface_spec_sha256（接口规范原文 hash，已导出到 provenance 与 capabilities[]，缺失为 null）；比对 = 演化脚本/测试做 JSON diff。加 iface_spec_sha256 是为了让宿主侧导出与作者侧 YAML 同源——否则锁通过也不证明两边说的是同一份接口。

validate --interface-lock —— 不加 CLI flag，10 行 diff 即可。注意 inject.required 混合了 YAML 行级声明（lib.rs:196），锁比对用插件声明口径或接受"行+插件"口径，ADR 写明。

范围限定：ExternService::methods() 返回 Vec<String>，只有方法名；参数/返回值在 ABI 上是 Config，宿主看不到形状。所以契约锁只能发现增删改名，发现不了参数类型变化。IO schema 级锁需要给 PluginDesc 按方法加 args/ret schema，属独立设计决策，不在阶段 1。

三轮交叉一致的结论

  • 三位评审独立指出同一 P0：cordis status --json 不能观测运行中宿主——v1 整条验收载体建立在错误的代码事实上。
  • R1 与 R2 独立指出 WP4 单层调用证明不了归因差异化——v2 加间接层是三方共识。
  • R2 的"定位收窄为部署地板"与 R1 的"砍 Python 驱动、进程内 e2e"互相印证：评估期不在宿主里跑，宿主就不需要被外部脚本实时驱动。
  • 未达成一致的点：R1 要砍契约锁 CLI 面、R2 要加方法面——v2 两者都取（无新 flag，但 status --json 多导出一项）。
