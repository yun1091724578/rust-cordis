## 2. 第一性约束

以下约束不随 roadmap 排期改变：

1. T1/T2 与宿主共享地址空间、权限和生命周期，`realm/scope` 不是安全边界。
2. T2 同步插件调用不可抢占；`DispatchPolicy` 只覆盖等待 `STATUS_PENDING`
   结算，不覆盖正在执行的 `apply`/回调。
3. T2 无法给单个插件设硬内存上限；cgroup/Job Object 限制整个宿主进程。
4. Rust 不保证无逻辑泄漏；只能证明已枚举路径回基线并做进程级观测。
5. `abi_version` 是线格式门禁；它不是插件 semver，也不证明行为兼容。
6. 同一 dylib 的 static 由所有实例共享；宿主只能保护已知的 volatile/
   callback 状态，插件作者自己的全局状态仍可能互相污染。
7. 来源治理（review、revision、hash、allow-list）不是执行隔离；
   流水线/密钥被攻破时，“可信”也会失效。

## 4. 当前执行顺序

### 第 0 步：ADR 0005 接受与产品口径收口

**出口**

- ADR 0005 从“提议”改为“已接受”；
- README / support-contract 增加“插件来源”行，状态为**声明**；
- 对外文案清除“安全隔离/沙箱/不会泄漏/版本不冲突/多租户安全底座”；
- README 明确“同步调用不可抢占”。

**不做**

- 不开始 T3 实现；
- 不承诺第三方插件生态；
- 不把“可信”写成“安全”。

### 第 1 步：P0 可信单租户底座

| 顺序 | 工作 | 关闭条件 | 依赖 / 边界 |
|---|---|---|---|
| 1 | 来源与身份 | manifest 有 plugin id / semver / source revision / artifact hash；loader allow-list；inspect/status 展示来源 | 来源治理不是安全隔离 |
| 2 | 每 App 的 dispatch policy | 不再依赖进程级 `set_dispatch_policy`；按 App/插件/方法配置；只覆盖挂起结算；长调用 opt-out | 不覆盖同步 `call` |
| 3 | 容量与准入 | instances/dispatches/队列有上限；超限可读拒绝；按 App/实例配置 | 不能给插件内存硬上限 |
| 4 | 锁纪律与故障注入 | 不持锁调插件；`call_inbound` 读锁路径审查；hang/panic/重入/卸载竞态有测试 | 锁中毒只在可达路径确认后定级 |
| 5 | 失败模式对外披露 | README/支持契约/ release 写明不可抢占、部署级 supervisor 兜底 | 不改写成“稳定保证” |

**P0 明确不包含**

- “有界专用线程池 + 超时放弃等待”作为抢占方案；
- per-plugin 内存上限；
- T3；
- 完整 semver 求解。

### 第 2 步：P1 长期运行与版本治理

| 顺序 | 工作 | 关闭条件 | 边界 |
|---|---|---|---|
| 6 | 插件 semver + 依赖求解 | `provides/requires` range、mount 前解析、歧义/缺失拒绝；`(id, version)` 身份 | ABI 仍精确匹配，先别引入冲突的 abi range 规则 |
| 7 | 版本矩阵 CI | 插件 vN 在宿主 vN/vN+1 各跑一遍；相邻冻结夹具 | 同版本加载不等于跨版本兼容 |
| 8 | 内存观测 | nightly RSS / dhat；真实 `open_staged` soak；泄漏预算 | 进程级观测不是 per-plugin 硬上限 |
| 9 | 性能 | 调用缓冲池化；高频 benchmark | 先有数据再谈“高效” |
| 10 | 故障隔离 | 若保留线程池，证明超时后不卸载/不释放插件；线程泄漏登记为已知代价 | 真正的抢占仍属 T3 |

### 第 3 步：agent 流处理

在 P0 信任边界和产品口径收口后，继续原有批次：

1. 有界增量交付：单事件/队列/累计输出/终止快照上限；慢消费者、sink 失败、
   无终止事件 EOF、终止写入与取消竞争；
2. 一个真实模型适配器：文本、工具参数增量、正常终止、流内错误、意外 EOF；
3. 取消与预算：模型等待、工具执行、sink 阻塞；首包/空闲/总运行超时；
   未知结果不自动重试。

**边界**：agent 流处理仍是仓外消费层；不把 `run.finished`/工具状态塞进 core。

### 第 4 步：T3 复评（条件触发）

只有当出现以下任一情况才启动：

- 第三方或模型生成插件进入运行时；
- 多租户/不可信输入/对外托管；
- 需要 per-plugin 内存上限、CPU 配额或可抢占执行；
- 生产 hang 导致宿主不可用；
- 独立部署/远程协议。

T3 方案至少比较：

- WASM（wasmtime + component model）：线性内存、fuel/epoch、WASI 能力；
- 子进程：崩溃隔离、可 kill，但仍需低权限/OS 沙箱和 IPC 收窄。

**在 T3 验收前，不发布“安全隔离/多租户”表述。**
